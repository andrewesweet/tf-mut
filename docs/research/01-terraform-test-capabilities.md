# `terraform test` — capabilities as of Terraform v1.15.8

Terraform v1.15.8 (released 8 July 2026) is the current stable release, and is the version
every claim below was verified against. Claims marked **[verified]** were established by
running the CLI locally rather than by reading documentation; several of them contradict
widely-repeated secondary sources.

## 1. Command surface

```
terraform test [options]
  -cloud-run=SOURCE      Execute remotely against an HCP Terraform / TFE private module
  -filter=FILE           Restrict execution to the named test file (repeatable)
  -json                  Machine-readable output
  -junit-xml=PATH        JUnit XML report (incompatible with -cloud-run)
  -no-color
  -parallelism=N         Concurrency within a run block's plan/apply (default 10)
  -test-directory=PATH   Test directory (default "tests")
  -var 'k=v'             Root module variable (repeatable)
  -var-file=FILE         Variable file (repeatable)
  -verbose               Emit the plan or state for each run block
```

The global `-chdir=DIR` option works with `test`, so the command can be driven against an
arbitrary directory without changing process working directory. **[verified]**

### `-filter` is file-scoped, not run-scoped **[verified]**

This is the single most consequential constraint for a mutation-testing harness, and it is
widely misreported. `-filter` accepts a *test file path*. Passing a run block name matches
nothing:

```
$ terraform test -filter=prod_floor
Success! 0 passed, 0 failed.          # exit code 0
```

A filter that matches nothing exits **0** with zero executed tests. Any harness that uses
`-filter` for test selection must independently assert that the executed-test count is
non-zero, otherwise a mis-selected filter silently reports every mutant as survived.

The practical consequence: **test selection granularity is the file, not the run block.**
Fine-grained selection has to be achieved by how test files are laid out, not by the CLI.

### Exit codes **[verified]**

| Outcome | Exit code |
| --- | --- |
| All runs pass | 0 |
| One or more runs fail an assertion | 1 |
| One or more runs error (invalid config, plan error) | 1 |
| Filter matched no files | 0 |

Exit code alone cannot distinguish *assertion failure* from *configuration error*. The JSON
stream can.

## 2. Test file schema

Taken from `internal/configs/test_file.go` at tag `v1.15.8` — the authoritative definition —
and cross-checked against the language documentation.

### File level

| Block / attribute | Notes |
| --- | --- |
| `test { parallel, skip_cleanup }` | File-wide execution settings |
| `variables { ... }` | Shared variable assignments for all runs |
| `variable "name" { ... }` | Test-scoped variable *declarations* (type, default, validation) |
| `provider "name" { ... }` | Real provider configuration; may reference prior run outputs (v1.7+) |
| `mock_provider "name" { ... }` | Mocked provider, labelled, optionally `alias` |
| `override_resource` / `override_data` / `override_module` | File-level overrides |
| `run "name" { ... }` | One or more; executed in declaration order |

### Run block

| Attribute | Values |
| --- | --- |
| `command` | `plan` \| `apply` (default `apply`) |
| `parallel` | bool (v1.9+) |
| `state_key` | string — selects which internal state file the run uses (v1.9+) |
| `providers` | map of config-provider-name → test-provider |
| `expect_failures` | list of traversals to custom conditions expected to fail |
| `skip_cleanup` | bool |

| Nested block | Notes |
| --- | --- |
| `variables { ... }` | Highest-precedence variable source |
| `module { source, version }` | Retarget the run at another module; **local paths and registry sources only** |
| `plan_options { mode, refresh, replace, target }` | `mode` is `normal` \| `refresh-only` |
| `assert { condition, error_message }` | Repeatable |
| `override_resource` / `override_data` / `override_module` | Run-scoped, takes precedence over file-level |
| `backend "type" { ... }` | Labelled backend for the run |

### Mocking

- `mock_provider "name"` substitutes a provider that reports the *same schema* as the real
  one, so configuration errors are still caught.
- `mock_resource "type" { defaults = { ... } }` and `mock_data "type" { defaults = { ... } }`
  supply values for computed attributes.
- Unspecified computed attributes are auto-generated by type: numbers → `0`, booleans →
  `false`, strings → an 8-character alphanumeric value, collections → empty.
- Mock data can be factored into `.tfmock.hcl` / `.tfmock.json` files and pulled in with a
  `source` attribute.
- `override_resource` / `override_data` / `override_module` bypass the provider entirely.
  Resources and data sources use `values`; modules use `outputs`. `override_during` selects
  `plan` or `apply` (default `apply`).

#### Mocks work with `command = apply` **[verified]**

Secondary sources (including several popular skill/agent packs) state that mock providers
are plan-mode only. They are not. A `mock_provider` block with `command = apply` executes
successfully and the mocked values surface in state and outputs:

```hcl
mock_provider "null" {
  mock_resource "null_resource" {
    defaults = { id = "mock-null-id" }
  }
}

run "apply_with_mocks" {
  command = apply
  assert {
    condition     = output.app_id == "mock-null-id"
    error_message = "mocked id surfaces in apply"
  }
}
```

This passes. It matters for mutation testing because `apply` mode exposes state and outputs
that plan mode leaves unknown, which widens the set of mutants a fully-mocked suite can kill.

The real limitation is different and worth stating precisely: mocks have no knowledge of the
*format* a real provider would produce, so generated values rarely resemble real ones, and
repeated blocks / nested attributes cannot be given per-instance values.

## 3. Machine-readable output

`terraform test -json` emits newline-delimited JSON. Observed message types **[verified]**:

| `type` | Payload key | Contents |
| --- | --- | --- |
| `version` | `terraform`, `ui` | Version handshake |
| `test_abstract` | `test_abstract` | Map of file path → list of run block names, emitted before execution |
| `test_file` | `test_file` | `path`, `progress` (`starting`/`teardown`/`complete`), `status` |
| `test_run` | `test_run` | `path`, `run`, `progress`, `elapsed`, `status` |
| `test_plan` | `test_plan` | *`-verbose` only.* `resource_changes`, `output_changes`, `relevant_attributes`, `provider_schemas`, format versions |
| `test_state` | `test_state` | *`-verbose` only.* `root_module`, `outputs`, `provider_schemas` |
| `test_summary` | `test_summary` | `status`, `passed`, `failed`, `errored`, `skipped` |
| `test_cleanup` | `test_cleanup` | `failed_resources[]` |
| `test_interrupt` | `test_interrupt` | State and planned resources at interruption |

Every message carries `@level`, `@message`, `@module`, `@timestamp`; test messages also carry
`@testfile` and, for runs, `@testrun`.

Two properties matter downstream:

1. **`test_summary` separates `failed` from `errored`.** An assertion failure and a
   configuration error are distinguishable without parsing human output. **[verified]**
2. **`-verbose -json` yields a full plan per run block.** *Correction (adversarial review
   C2, 2026-08-15):* this document originally described `relevant_attributes` as "a coverage
   signal". It is not — it is the refresh/targeting dependency set, identical across run
   blocks, blind to assertion reads, and absent from apply-mode `test_state`. Coverage
   signals must come from `resource_changes` plus the test files' assertion ASTs. Note also
   that each `-verbose` message embeds the full `provider_schemas` — 14.5 MB for
   `hashicorp/aws` — which dominates the cost of verbose runs (review C1).

### Error propagation within a file **[verified]**

When one run block errors, subsequent run blocks in the same file are **skipped**, not run:

```json
{"status": "error", "passed": 0, "failed": 0, "errored": 1, "skipped": 3}
```

A harness must therefore treat `errored` as a terminal condition for the file and must not
infer anything about the skipped runs.

## 4. Module resolution and `.terraform`

`terraform init` writes `.terraform/modules/modules.json`. For local module sources the
recorded directory is **relative to the working directory** **[verified]**:

```json
{"Modules":[
  {"Key":"","Source":"","Dir":"."},
  {"Key":"net","Source":"./modules/net","Dir":"modules/net"},
  {"Key":"test.tests.unit.module_directly","Source":"./modules/net","Dir":"modules/net"}
]}
```

Note the third entry: a `module { source = "./modules/net" }` block inside a run block is
registered under the key `test.<dir>.<file>.<run>`, and also resolves relatively.

Because these paths are relative, a `.terraform` directory can be **shared read-only across
many working directories** and each directory still uses *its own* copy of the local module
source. This is the property that makes cheap mutant sandboxes possible (see
`04-harness-spike.md`).

## 5. Gaps in the current release

Relevant open upstream issues, by community reaction count:

| Issue | Title | Reactions |
| --- | --- | --- |
| [#34073](https://github.com/hashicorp/terraform/issues/34073) | Add ability to skip teardown | 47 |
| [#33786](https://github.com/hashicorp/terraform/issues/33786) | Dump complete state file when destroy fails | 29 |
| [#34622](https://github.com/hashicorp/terraform/issues/34622) | Custom teardown scripts | 21 |
| [#36189](https://github.com/hashicorp/terraform/issues/36189) | Omit targeted resources from mocking | 20 |
| [#34500](https://github.com/hashicorp/terraform/issues/34500) | Validate plan diffs / attribute changes | 18 |
| [#37605](https://github.com/hashicorp/terraform/issues/37605) | **Native `terraform test` code coverage** | 8 (open since Sept 2025) |

There is **no native coverage capability and no accepted proposal shipping one**. Any measure
of "are my Terraform tests any good?" today has to be built outside the CLI.

Experimental work visible in v1.16 alphas — `terraform test cleanup`, `backend` blocks in run
blocks, skip-cleanup — is not in stable and should not be depended on.
